# ADR-0001：静态语义、闭世界、runtime 属于语言

- 状态：已接受
- 日期：2026-08-30

## 背景

Gugu 要表面像 Go / JS·TS / Lua，性能锚点却是 Rust / C++。常见失败模式是：语法简化的同时把语义做成动态对象、开世界加载、或把 runtime 做成另一个语言里的 VM，然后用 FFI 往返。

## 决策

- 语法可以省略注解；运行时语义必须是健全静态类型 + 编译期已知布局。
- 链接前闭世界：全部可达函数与类型可枚举。禁止 eval、改类布局、加载未知 Gugu 代码。插件只走窄 C ABI。
- 泛型单态化；默认不装箱。
- 分配对编译器可见：逃逸分析、栈分配、arena；GC 若存在，也必须是精确的，且写屏障是 IR 原语。
- 目标镜像 = 用户码 + 用本语言写的 runtime + rt0。编译器用 Rust；runtime 不用 Rust 写两遍。
- 从一开始就规划 `unsafe` 与 intrinsic（换栈、写屏障、裸分配）。
- 不用 LLVM。自研 x86_64 codegen。尽可能不依赖系统链接器：全程序编译后自己写出 ELF/PE。
- 没有对象系统。闭包一等。

## 替代方案

本节为 2026-09 文档整理时补记：列出决策时已隐含拒绝的方向，便于后续对照；非决策当时的原始记录。

- **渐进类型或动态对象模型（JS·TS 式）**：与设计公理「健全静态类型」「静态布局」直接冲突，编译期可验证性与性能锚点都无法满足。
- **字节码 VM 宿主 + 开世界加载（JVM 式）**：违背闭世界公理与「轻量静态镜像」目标；JIT 只能作为同一闭世界程序的执行实现细节存在。
- **Rust 式所有权/借用检查作为内存模型**：与「分配不增加所有权语法」公理冲突；传递语义后续由 ADR-0003 单独决定。
- **以 LLVM 与系统链接器为后端**：镜像体积、外部工具链依赖和确定性产物要求冲突；决策保留自研 x86_64 后端与直接镜像写出。
- **保守式/非精确 GC**：无法提供精确根与移动语义，闭世界类型元数据的优势也被浪费；写屏障必须作为 IR 原语。

## 后果

- 对象模型（struct/enum vs table）和内存管理（GC vs 所有权 vs 混合）决定性能上限，必须先于 JIT/LLVM 这类后端选择被写进规范。
- 编译器必须做全程序可见的优化，而不是「一个文件一个 `.o` 再 ld」。
- 标准库、GC、调度器的引导问题由 rt0 + `unsafe` 解决，不引入第二套宿主运行时。
- Windows：PE 导入薄 kernel32/ntdll，不扫 syscall 号，默认不链 CRT。

## 实施状态

前端（词法/语法/名称/类型/特化/模式）、HIR→GIR→LIR、闭世界单态化与编译缓存、包/锁/vendor 管理，以及 runtime 契约与确定性参考模型（调度、channel、GC 屏障平面、SharedHeap 稳定句柄转发闭环）已实现；`gugu build` 产出并校验镜像计划。自研后端的机器码生成与 ELF/PE 写出（roadmap 后端阶段）尚未实现，GC 的指针压缩、credit termination 等收尾项按 ADR-0009 顺序推进中。
