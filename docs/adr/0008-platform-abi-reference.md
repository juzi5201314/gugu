# ADR 0008：平台与 ABI 参考采用单章二维目标模型

- 状态：已接受
- 日期：2026-08-31
- 相关规范：[平台与 ABI 参考](../src/spec/platform-abi.md)

## 背景

现有规范分别在程序模型、类型、unsafe、并发、包构建和工具链章节中描述平台与 C ABI。两个已支持目标使用 `x86_64-linux` 和 `x86_64-windows`，但“目标三元组”、目标派生属性、C 数据模型、调用约定和 ABI 稳定边界没有单一规范入口。继续分散追加条款会让实现者无法判断哪些内容是 Gugu 契约、哪些内容只是平台实现细节。

Rust 将目标支持、`repr(C)` 布局和外部 ABI 分开承诺，并把内部 ABI 留给编译器；Go 将 `GOOS` 与 `GOARCH` 分开，用构建约束选择平台代码，并把 `ABIInternal` 视为编译器/运行时内部协议。这两种实践都适合 Gugu 的闭世界编译模型，但不能直接照搬 Rust 的完整 target triple 或 Go 的开放端口矩阵。

## 决策

1. 新增单一规范章节 `docs/src/spec/platform-abi.md`，作为平台与外部 ABI 的统一查阅入口。
2. 目标由 `arch × os` 二维注册表表示，规范名称为 `<arch>-<os>`；本版本只登记 `x86_64-linux` 与 `x86_64-windows`，不接受 LLVM 四段 triple，也不定义 tier-2/tier-3。
3. 调用约定采用桥接写法：引用 System V AMD64 psABI 与 Microsoft x64 的通用算法，但规范性固定 Gugu 类型的可表示性、C 数据模型、聚合边界、隐藏返回指针、栈约束和目标差异。
4. ABI 稳定面仅包括 `extern "C"`、明确的 C 布局、外部符号和镜像入口/保留节；Gugu 内部 ABI、默认布局、句柄对象、vtable、TypeId、栈图编码和内部符号不稳定，跨版本必须整体重编译。
5. `std.ffi` 提供透明 C 类型别名族，并在规范中固定 LP64 与 LLP64 的映射，特别是 `c_long`、`c_wchar`、`c_size` 等目标相关类型。
6. `os` 与 `arch` 是本版本仅有的内建平台 cfg 键；指针宽度、字节序和 C ABI 等派生属性由目标注册表定义，不允许自定义 cfg 覆盖。

## 未采用的方案

- **拆分平台章与 ABI 章**：会增加交叉引用和重复维护；当前目标数量不足以抵消拆分成本。
- **完整复制平台 ABI 算法**：会把外部规范的机器细节固化进语言规范，并产生长期同步风险；Gugu 只固定自身的桥接规则。
- **仅声明遵循平台 ABI**：无法为 sret、聚合边界、`i128` 和镜像写出提供可执行依据。
- **从一开始支持完整环境 triple 与自定义目标**：会把环境维度扩散到清单、缓存、cfg 和闭世界镜像；新增目标待真实实现需求出现后登记。
- **定义版本化 Gugu 内部 ABI**：需要同时固定 GC、泛型单态化、运行时元数据和栈图协议，超出当前闭世界编译目标。

## 后果

- 实现者有一个规范性入口，平台文档只需补充未被 Gugu 表格覆盖的通用算法。
- Linux LP64 与 Windows LLP64 的 C 绑定可以复用同一套别名名称，不再要求用户手工猜测 `long` 宽度。
- 新架构或操作系统必须先进入目标注册表，并同步 runtime、镜像写出器、标准库和测试；不能用自定义 cfg 宣称支持。
- C varargs、Gugu 函数句柄作为 C 回调、`long double` 和 Gugu-to-Gugu 跨版本链接继续不属于当前 ABI 表面。
